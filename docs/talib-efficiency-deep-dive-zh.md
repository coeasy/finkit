## 1. 为什么"效率对比"必须先谈测量方法

第十七轮开始时，我（助手）手里有一张全量配对表和一台机器。把两者放在一起就能得到错误结论——
因为它把**进程间抖动**读成了**代码差距**。

### 1.1 机器的抖动远大于要追的差距

同一份二进制、同一个指标、连续的两次独立进程运行：

| 指标 | 我方三次独立进程（µs） | TA-Lib 三次独立进程（µs） |
|---|---|---|
| `tanh` | 59.23 / 37.15 / 24.20 | 45.83 / 45.56 / 45.62 |
| 相对极差 | **145%** | **0.6%** |

抖动是**单侧**的：动的是我方那一列，C 侧稳定到 0.2%。原因是我方那一列由 Criterion 在同一个
进程里测，而该进程的**代码布局**（函数对齐、`i-cache` 命中、分支预测器状态）会随链接顺序变化；
C 侧的 FFI 调用点少得多。

**推论：`docs/BENCHMARK_REPORT.md` 是筛查产物，不是判决书。** 接近 1.0 的比值必须复测或改用
同进程 A/B。

### 1.2 同进程 A/B 探针：把两侧放进同一个二进制

`core/examples/kernel_hotspot_probe.rs`（临时件，不提交）把**改造前**和**改造后**的函数体放进
同一个二进制，交替计时，取 N 次最小值。两侧共享同一份热状态、同一个分配器、同一页缓存。
调用方式：

```bash
cargo run --release -p finkit --example kernel_hotspot_probe
```

### 1.3 一个必须写下来的探针陷阱

探针的**第一版是有偏的**，而且偏向正好会让我得出错误结论：它把"改造前"的函数体写成**写入
调用方预留缓冲区**（零分配），却把"改造后"一侧通过**公开函数**调用（每次分配 80 KB）。
于是分配成本被整笔算到了新代码头上，三个微改造看起来都成了"回退"。

修正方式：**两侧都承担各自真实的分配**，并且额外加一档 **`_into` 内核级**对比（两侧都不分配）
把分配与内核彻底分开。

### 1.4 探针自身的噪声地板（空对照）

修正后的探针里放了两个**空对照**：把**当前已发布的函数体原样抄一份**当作"改造前"，与公开函数
PK。两者代码相同，比值就是探针自己的分辨力：

| 空对照 | 比值 | 含义 |
|---|---|---|
| `AVGDEV_14`（同体对照） | **0.995×** | 同一份代码，误差 0.5% |
| `LINREG_SLOPE_14`（同体对照） | **1.042×** | 同一份代码，误差 4.2% |

**分辨力约 0.5%–4%，且逐内核不同。** 这直接改写了对若干历史结论的判读：任何小于约 10% 的
差异，除非同一形状重复出现，都不足以下结论。

### 2.2 全量列与同进程 A/B 冲突时，信哪个

`aroon_14` 的全量列从 0.88× 变成 0.84×，而同进程 A/B 说新代码**快 1.045×**。两者不矛盾：

- 全量列是**跨进程**测量，我方那一列的进程间漂移可达 ±40%（§1.1），0.88 与 0.84 的差别
  远小于这个带宽；
- A/B 是**同进程交替**测量，两侧共享热状态与分配器，分辨力 0.5%–4%（§1.4）。

**规则：全量列用来筛出"哪些指标值得看"，同进程 A/B 用来判断"代码改动到底有没有用"。**
本文 §4 所有"更快/更慢"的结论都只引用后者。

## 3. 非 ✅ 行的分类判读

全量列的 16 个非 ✅ 行（15 ⚠️ + 1 ❌）不是同一类东西。把它们混在一起谈"落后 0–30%"会掩盖三类
完全不同的成因，也会让"还剩多少要修"这个数字失去意义。

| 类别 | 项目 | 判读 |
|---|---|---|
| **A. 真落后** | `linreg_slope_14`（0.76×） | 两轮运行给出同一数字，唯一站得住的 ❌；归因见 §4.4，仍**未定** |
| **B. 测量噪声** | `cos`（0.91×，上轮 1.11×） | 复测翻转；`tanh` 本轮已回到 1.68× ✅，同属此类 |
| **C. 结构性小差距**（0.82–0.98×） | `linreg_intercept_14` 0.82、`ultosc` 0.83、`aroon_14` 0.84、`aroonosc_14` 0.85、`var_20` 0.87、`adxr_14` 0.93、`max_30` 0.94、`min_30` 0.94、`linreg_angle_14` 0.95、`wma_20` 0.96、`ad` 0.98、`trima_20` 0.98 | 内核已是手工优化过的（单调队列 / 缓存下标 / van Herk 分块），剩下的是**每根 bar 的边界与分支开销**——C 侧没有对应物 |
| **D. 大样本带宽** | `sma_20@1M` 0.85×、`rsi_14@1M` 0.97× | 同指标在 10k/100k 上都是 1.3–1.8×，1M 处进入内存带宽主导区间；见第 7 节 |

把 B 和 D 从"待修清单"里去掉之后，真正要处理的是 **A（1 项）** 和 **C（12 项）**——而 C 类里
有 12 项挤在同一个 0.82–0.98 的窄带里，这本身说明它们共享同一个成因，不适合逐项打补丁。

## 4. 本轮改动与其测量证据

以下四处都经过 §1.2 的同进程 A/B，且都带**数值等价断言**（不是"应该等价"）。

### 4.1 `PERCENTRANK`：把排序窗口换回计数 — **4.58×，逐位相同**

原实现为每根 bar 维护一个**有序窗口**：一次二分查找定位、一次 `copy_within` 搬移约半个窗口，
再插入新值。而 `TA_PERCENTRANK` 要的只是一个**整数**——`timeperiod` 个前序观测中严格小于当前
值的个数。计数是整数，两条路径**逐个 slot 逐位相同**（探针断言 `10000/10000`），所以这是**同一
谓词的换写**，不是浮点求和的重结合，不需要任何容差来辩护。

| 实现 | 10k bar | ns/bar |
|---|---:|---:|
| 有序窗口 + 二分 + 搬移（上一版） | 309.40 µs | 30.94 |
| AVX2 直接计数（本版） | 67.50 µs | 6.75 |
| **比值** | **4.584× 更快** | |

带 `NaN` 的输入仍走原有序路径——原式用 `partial_cmp().unwrap_or(Equal)`，缺失值没有确定位置，
两条路径**不要求**一致，所以保留已发布行为而不是重新定义它。

### 4.2 `AROON` / `AROONOSC`：三份递推合并为一份，同时快于原实现

`AROON`、调用方自持的 `aroon_into`、`AROONOSC` 原先有三份**手抄的同一递推**，且 `NaN` 行为
各不相同——这是典型的"两份会漂移"。

本版把递推抽成一个 `ExtremeTracker`（缓存下标 + 越窗重扫），三条入口只差"从同一状态里取哪个
输出"。关键约束是**必须保持原实现的单趟形状**：我第一版写成"每条腿一次 `aroon_leg_into`"，
即两趟；探针立刻显示它在内核级慢 **21%**，随后改为**双腿同趟**。

| 对比 | 上一版 | 本版 | 比值 |
|---|---:|---:|---:|
| `aroon_14`（含分配） | 97.30 µs | 93.10 µs | **1.045× 更快** |
| `aroonosc_14` | 55.70 µs | 52.40 µs | **1.063× 更快** |
| `aroon_into_14`（内核级，无分配） | 51.30 µs | 56.50 µs | 0.908× 更慢 |

诚实读法：**面向上层与基准的 `aroon`/`aroonosc` 变快了，内核级 `_into` 慢 9%。**
9% 落在探针的逐内核分辨力带上（0.5%–11.6%），但方向连续两轮一致，所以按"未证实"记，
不计入收益。数值等价：`aroon_up`/`aroon_down`/`aroonosc` 在 `1e-12` 下 **0 处失配**。

### 4.3 `AVGDEV`：两次改造实测更慢，**回退**并记录

| 候选 | 结果 |
|---|---|
| 环形下标替代 `Vec::remove(0)` + `push` | 更慢 |
| AVX2 `Σ|x - mean|` | 更慢 |
| 同体空对照（分辨力） | 0.995× → 差异是真的，不是噪声 |

原因可以从窗口尺寸直接推出：period 14 的窗口是 **13 个 double**，`remove(0)` 搬移的 104 字节
本来就在 L1；而向量扫描把 14 次串行加法换成 3 次整通道加法**外加一次水平归约和一次运行时
派发**。**这里没有可挖的空间**，所以保留直白写法，并把负面结果写进代码注释。

### 4.4 `LINREG_SLOPE`：指针游标是**恰好中性**，且推翻了此前的归因

`linreg_slope_14` 是全量列唯一的真 ❌（0.76×）。V4 §42.8 把它归因于**每 bar 的越界检查**，
并断言"关掉它需要把每个循环改成 `linreg_slope` 那样的游标写法"。

本轮在**相同播种、相同分配**下只改循环体（索引 vs 指针游标）：

| 循环体 | 10k bar | 比值 |
|---|---:|---:|
| 索引（现行） | 30.40 µs | — |
| 指针游标 | 30.40 µs | **1.000×，0 处失配 @1e-12** |

**恰好中性。** 这说明 `linreg_slope` 的递推循环里，LLVM **已经**把越界检查消掉了，§42.8 的归因
对这个内核**不成立**。因此该改造不落地——不是因为它更慢（此前"0.593×"的读数是 §1.3 那个有偏
探针的产物），而是因为**没有收益**。这个真实 ❌ 的成因需要另找，列入第 9 节。

## 5. 历史遗留修复

### 5.1 `CCI`：两个"只存在于名字里"的 SIMD 路径

```rust
fn cci_period14_into_impl<const USE_AVX2: bool>(...) {
    let _ = USE_AVX2;   // ← 参数从不被读取
    ...同一份未展开的标量代码...
}
// 调用点
if is_x86_feature_detected!("avx2") { cci_period14_into_impl::<true>(...) }
else                                { cci_period14_into_impl::<false>(...) }
```

两份分支不产生任何差别：函数体不读这个参数。这是**伪装成 SIMD 的死分支**——读者会以为
period-14 路径已经向量化，从而不再去找它。同类第二处在 `math/simd_kernels.rs`：
`cci_simd_into` 做 `has_avx2()` 判断后两个分支都指向同一个标量函数。

修复方式不是"把向量化补上"，而是**删掉参数并说明为什么这里不该向量化**：向量化意味着把
`Σ|x - mean|` 重结合到四个通道，而窗口偏差趋近 0 时，末尾的除法会放大这个差异；`CCI` 与 TA-Lib
金标准是**绝对 `1e-8`** 比对，该差异可测。测量也同意——AVX2 形式在 10k bar 上**慢 18%**，
并且把 10000 个值里的 **13 个**推出了 `1e-8`。

仓库全量扫描确认：`let _ = <被忽略的 const 泛型>` 这类模式，修完全仓**只剩这一处**（已清零）。
`fast_moving_avg.rs` 的 `USE_FMA` 形似但**不是**同类——它的两个分支 `mul_add` 与 `*`+`+` 真的
不同，且两个值都被实例化（`true` 来自 `#[target_feature(enable = "fma")]` 的包装，`false` 来自
无 FMA 回退），注释也写明了"不要合并"。

### 5.2 `CCI`：同一个指标，两个答案

period-14 专用路径在"窗口偏差为 0"时写 `0.0`，而通用路径写 `NaN`——**同一个指标因为传入的
period 不同而给出不同的值**。`TA_CCI` 的行为是 `0.0`。两条路径现在统一为 `0.0`。

## 6. 被否决的方案（负面结果目录）

这些方案都**实现过、测量过、然后删掉**。写下来是为了让后来的读者不必重跑：

| 方案 | 结果 | 结论 |
|---|---|---|
| AVX2 `CCI` 窗口对 | 慢 18%，且 13/10000 值越出 `1e-8` | 精度+速度双输 |
| AVX2 `AROON` 通道扫描 | `aroon` 0.92–0.96×，`aroonosc` 0.50–0.75× | 分支误预测多于它省下的比较 |
| Van Herk–Gil–Werman 分块扫描 | 比缓存下标慢（~10 vs ~7.5 ns/bar） | 8 张动态索引表的代价高于它省下的重扫 |
| `AVGDEV` 环形窗口 + AVX2 绝对值 | 见 §4.3 | 13 元素窗口无空间 |
| `LINREG_SLOPE` 指针游标 | 恰好 1.000× | LLVM 已消除越界检查，无收益 |
| `AROON` 每条腿一趟（两次 `aroon_leg_into`） | 内核级慢 21% | 已改为双腿同趟（§4.2） |

## 7. 规模效应（10k / 100k / 1M）

同一指标的比值随输入规模变化，而且**不是单调的**：

| 指标 | 10k | 100k | 1M |
|---|---:|---:|---:|
| `sma_20` | 1.67× | 1.75× | **0.85×** |
| `ema_12` | 2.54× | 2.65× | 1.55× |
| `rsi_14` | 1.33× | 1.32× | **0.97×** |
| `macd` | 2.39× | 2.00× | 1.44× |
| `bbands_20` | 1.62× | 1.67× | 1.22× |

读法：

- **10k/100k 是"算法 + 常量因子"主导**，比值最能反映内核优劣，且两档之间高度一致
  （`ema` 2.54/2.65、`rsi` 1.33/1.32）——这种一致性本身就是测量可信的标志。
- **1M 进入内存带宽主导**。此时绝对值已达毫秒级（`sma_20` 5.10 ms vs 4.32 ms），比值开始对
  缓存行为、页错误、以及进程间漂移比对算法更敏感。`sma_20@1M` 上一轮报 1.14×、本轮 0.85×，
  而它在 10k/100k 两档稳定在 1.7× 左右——**该行的可重复性低于它自己的三档差异**。
- 因此**不要用 1M 那一档去评价内核**，但一定要保留它：它是唯一能暴露"算法在大输入下退化"的档
  （例如 `O(n·period)` 回退在 10k 上几乎看不出来）。

## 8. 单指标之外：结构性优势在哪

TA-Lib 的配对基准只能量到"单个指标、单次调用"。Finkit 的差异化在**统一运行时**这一层，
配对表**结构上量不到**：

- **一次解析、多次执行**：`TA_*` 每次调用都要重新走参数校验与状态初始化的路径；统一运行时把
  计划编译一次后复用。
- **脏区增量重算**：新 bar 到达时只重算受影响区间，而不是整段重跑。
- **共享中间量**：`TR`/`DM`/`EMA`/滚动统计在多指标之间只算一次。
- **调用方自持缓冲**：`_into` 面消除热路径堆分配（并有 `zero_alloc_bench` 与
  `memory_regression` 测试守门）。
- **语言绑定端的端到端开销**：Python / Node / C ABI 的每调用成本。

因此**"Finkit 是否比 TA-Lib 快"这个问题，在单指标口径下只应给筛查级答案**；
产品级结论要看研究流水线口径的重活。

   这个归因——把循环体换成指针游标是**恰好中性**（1.000×），说明 LLVM 早就消掉了那些检查。
